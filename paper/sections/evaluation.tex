In this section, we describe the benchmarking methodology used to evaluate modularity-based graph clustering algorithms under controlled and reproducible conditions. A central contribution is the integration of 17 clustering algorithms behind a unified benchmarking interface, enabling a fair comparison across diverse implementations. In addition to enabling the experiments presented in this survey, it will also serve as an openly available resource for future work on graph clustering, simplifying the evaluation of older methods on new data or machines. This section also includes details on the datasets we used to evaluate the clustering algorithms and the computational environment.

\subsection{Benchmark Interface}

As shown in Table~\ref{tab:comp}, over half of the clustering algorithms in the literature lack ready-to-use interfaces for clustering new data. Furthermore, among those with properly documented code, there are wide differences in the input graph format, output formats, and the additional information they report, such as time and memory consumption. This lack of standardization complicates fair benchmarking, as differences in preprocessing, reporting, and resource accounting can substantially affect observed performance.

To address this problem, we aim to provide an interface with a single common input and output format and consistent time and memory monitoring. The interface exposes a common set of inputs, while allowing solver-specific parameters to be provided when applicable.

\[\textsc{Cluster}(G, T_{\max}, p, k, M_{\max}, \mathcal{F})\]

Where $G$ is the input graph, $T_{\max}$ is the wall-clock time limit, $p$ is the number of threads available to the algorithm, $k$ is the number of clusters to compute, $M_{\max}$ is the memory limit in gigabytes, and $\mathcal{F}$ are the graph features. Parameters $p$, $k$, and $\mathcal{F}$ are only used by a subset of the solvers. From Table~\ref{tab:comp}, parallel solvers use $p$, those that compute a fixed number of clusters use $k$, and any solver that uses graph features can optionally accept $\mathcal{F}$. When $\mathcal{F}$ is not provided, but the solver expects features, a single 1.0 value is assigned to each vertex as the feature. This interface is designed to capture the most common operational requirements across clustering algorithms while enforcing consistent resource limits and output reporting.

Regarding code changes, we have tried to make as few modifications to the original source code as possible. Whenever possible, we use the authors' implementations or the most commonly used library implementation. The exact setup for each algorithm is described in our openly available GitHub repository\footnote{\url{https://github.com/KennethLangedal/Clustering}}. We make only minimal, deliberate modifications where necessary to ensure consistent timing, memory accounting, and output quality measures based on the following rules:

\begin{itemize}
    \item Parsing the input and writing the output to a file is not counted in the timing of the algorithm.
    \item For search-based algorithms that always run for the entire $T_{\max}$ duration, the recorded computation time is defined as the point in time when the best solution was found.
    \item Learning-based methods that train a neural network as part of the algorithm will break the training loop at $T_{\max}$, and use the current model at that time to produce the final clustering.
\end{itemize}

\subsection{Parameter Settings}

As much as possible, we try to use the default configurations for all algorithms tested. In the following we detail the exact parameters chosen for each algorithm. Algorithms that are not listed do not expose any parameters.

\paragraph*{\textbf{Parameter Selection Policy.}}
To reflect how algorithms are typically used in practice, we deliberately avoid any dataset-specific or instance-specific parameter tuning. Our goal is to benchmark available implementations as they are, rather than hypothetical optimal configurations that would require extensive tuning effort.

\begin{itemize}
    \item \textsc{Walktrap}: walk length $=4$.
    \item \textsc{Louvain}: resolution $=1$.
    \item \textsc{Hollocou}: $v_{\max}=10\,000$.
    \item \textsc{VieClus}: time limit $=1$ hour.
    \item \textsc{Leiden}: resolution $=1$, $\beta=0.02$, iterations $=2$.
    \item \textsc{DMoN}: 1 hidden layer (64), 1000 epochs, lr $=0.001$.
    \item \textsc{CommDGI}: 1 hidden layer (512), 1000 epochs, lr $=0.001$.
    \item \textsc{GNNS}: \textsc{GNNS100} variant.
    \item \textsc{UCoDe}: 2 hidden layers (256), 1000 epochs, lr $=0.001$.
    \item \textsc{DGCluster}: hidden layers (256, 128), 300 epochs, lr $=0.001$.
    \item \textsc{MAGI}: hidden layers (512, 256), 100 epochs, lr $=0.01$.
    \item \textsc{Bayan}: Gurobi ILP solver~\cite{gurobi}, gap $=10^{-4}$, resolution $=1$.
    \item \textsc{CluStRE}: light mode, modularity objective.
    \item \textsc{LIM}: 1 hidden layer (512), 1000 epochs, patience $=200$, \hbox{lr $=0.001$.}
\end{itemize}

For stochastic algorithms with an explicitly specified seed, we use the run ID as the seed for each of the five runs. While many of these algorithms include multiple configurations, we use either the configuration recommended by the authors or the default configuration provided with the implementation.

\subsection{Dataset}

We consider three datasets commonly used in the literature. The first set consists of 10 real-world graphs with known community labels; we refer to this dataset as the \textsc{Ground-Truth} graphs. The machine learning algorithms commonly use these graphs, and the details of the instances are shown in Table~\ref{tab:ground_truth_graphs}. Next, we consider the instances used in the 10th DIMACS implementation challenge on graph clustering; we call this dataset \textsc{DIMACS} graphs. This dataset is popular among the classical modularity optimization methods, and the details of these graphs are shown in Table~\ref{tab:dimacs_instances} in the appendix. Finally, we use a dataset of synthetically generated graphs with node features generated using the attributed, degree-corrected stochastic block model~\cite{adcsbm2022} (ADC-SBM). This generator allows us to explore the algorithm's sensitivity to noise in both the graph and features.

\subsection{Computational Environment}

All algorithms are evaluated on the same machine to eliminate variability due to hardware differences and ensure fair comparison. While some methods could potentially benefit from specialized accelerators such as GPUs, we intentionally restrict all experiments to a shared CPU-based environment to maintain consistency across algorithms. We use a machine with an AMD EPYC 9754 128-core processor with 755 GB of memory, running Ubuntu 24.04.3 with Linux kernel 6.8.0-87. For algorithms with compiled software, we use GCC version 13.3.0, and for Python implementations we use Python version 3.12.3.

In order to speed up experiments, we evaluate three algorithms in parallel. For parallel algorithms, we evaluate them both sequentially and using 16 threads. If an algorithm exceeds 250 GB of memory usage on an input instance, it is killed and recorded as \emph{memory limit exceeded} for that graph. Similarly, we assign each algorithm a time limit of 1 hour per input graph. Unlike the memory limit, we allow limited flexibility for time limits due to the structure of learning-based methods, which often train for a fixed number of iterations. Only if an algorithm overshoots the time limit by more than 50\% do we kill the process and record that instance as \emph{time limit exceeded}.

For algorithms that needs to be told the number of clusters, we either provide the exact number when ground truth labels are known, or 16 clusters otherwise, as is commonly used in the literature. Since several of the algorithms are Stochastic, we report the best result over five runs to reflect the maximum achievable solution quality under the given resource constraints, which is standard practice in modularity optimization. In addition to measuring modularity as defined in Section~\ref{sec:preliminary}, we aslo use Normalized Mutual Information (NMI) between the computed clusters and ground-truth labels and F1 scores between adjacent pairs of vertices.

\paragraph*{\textbf{Performance Profiles}}

Performance profiles are well suited for benchmarking diverse algorithms, as they summarize relative performance across instances without requiring direct aggregation of objective values~\cite{perf2002}. A performance profile assigns each included algorithm a non-decreasing, piecewise-constant function. The y-axis represents the fraction of graphs where the objective value is better than or equal to $\tau$ times the best observed objective function value from any algorithm. Reading a performance profile, an algorithm performs well if it achieves lower $\tau$ values for higher fractions of instances.
