In the following section, we present the evaluation methodology used in this experimental survey. The main contribution is the adaptation of 17 clustering algorithms behind one unified interface. In addition to enabling the experiments presented in this survey, it will also serve as an openly available resource for future work on graph clustering, simplifying the evaluation of older methods on new data or machines. This section also includes details on the datasets we used to evaluate the clustering algorithms and the computational environment.

\subsection{Implementation}

As shown in Table~\ref{tab:comp}, over half of the clustering algorithms in the literature lack ready-to-use interfaces for clustering new data. Furthermore, among those with properly documented code, there are wide differences in the input graph format, output formats, and the additional information they report, such as time and memory consumption. As a result, it can take significant effort to get a particular algorithm to run and extract the desired measurements.

To address this problem, we aim to provide an interface with a single common input and output format and consistent time and memory monitoring. The interface exposes a common set of inputs, while allowing solver-specific parameters to be provided when applicable.

\[\textsc{Cluster}(G, T_{\max}, p, k, M_{\max}, \mathcal{F})\]

Where $G$ is the input graph, $T_{\max}$ is the wall-clock time limit, $p$ is the number of threads available to the algorithm, $k$ is the number of clusters to compute, $M_{\max}$ is the memory limit in gigabytes, and $\mathcal{F}$ are the graph features.

Parameters $p$, $k$, and $\mathcal{F}$ are only used by a subset of the solvers. From Table~\ref{tab:comp}, parallel solvers use $p$, those that compute a fixed number of clusters use $k$, and any solver that uses graph features can optionally accept $\mathcal{F}$. When $\mathcal{F}$ is not provided, but the solver expects features, a single 1.0 value is assigned to each vertex as the feature.

Regarding code changes, we have tried to make as few modifications to the original source code as possible. Whenever possible, we use the authors' implementations or the most commonly used library implementation. The exact setup for each algorithm is described in our openly available GitHub repository\footnote{\url{https://github.com/KennethLangedal/Clustering}}. We did, however, make some deliberate changes to ensure consistent timing and quality measures.

\begin{itemize}
    \item Parsing the input and writing the output to a file is not counted in the timing of the algorithm.
    \item For search-based algorithms that always run for the entire $T_{\max}$ duration, the recorded computation time is defined as the point in time when the best solution was found.
    \item Learning-based methods that train a neural network as part of the algorithm will break the training loop at $T_{\max}$, and use the current model at that time to produce the final clustering.
\end{itemize}

\subsection{Parameter Settings}

As much as possible, we try to use the default configurations for all algorithms tested. In the following we detail the exact parameters chosen for each algorithm. Algorithms that are not listed do not expose any parameters.

\begin{itemize}
    \item \textsc{Walktrap}: The length of random walks is set to \numprint{4}.
    \item \textsc{Louvain}: The resolution limit is set to \numprint{1}.
    \item \textsc{Hollocou}: We set $v_{max} = \textsc{10000}$.
    \item \textsc{VieClus}: The timelimit is set to one hour.
    \item \textsc{Leiden}: The resolution limt is set to \numprint{1}, $\beta = \numprint{0.02}$, and number of iterations is set to \numprint{2}.
    \item \textsc{DMoN}: We use one hidden layer with 64 neurons and train for \numprint{1000} epoch with learning rate \numprint{0.001}.
    \item \textsc{CommDGI}: We use one hidden layer with 512 neurons and train for \numprint{1000} epoch with learning rate \numprint{0.001}.
    \item \textsc{GNNS}: We use the version \textsc{GNNS100}.
    \item \textsc{UCoDe}: We use two hidden layers with 256 neurons and train for \numprint{1000} epoch with learning rate \numprint{0.001}.
    \item \textsc{DGCluster}: We use one hidden layer with 256 neurons followed by another hidden layer with 128 neurons and train for \numprint{300} epoch with learning rate \numprint{0.001}.
    \item \textsc{MAGI}: We use one hidden layer with 512 neurons followed by another hidden layer with 256 neurons and train for \numprint{100} epoch with learning rate \numprint{0.01}.
    \item \textsc{Bayan}: We use the Gurobi optimizer for ILP solving~\cite{gurobi}, acceptable optimality gap of \numprint{0.0001}, and a resolution limit set to 1.
    \item \textsc{CluStRE}: We use the light mode with the modularity objective function.
    \item \textsc{LIM}: We use one hidden layer with 512 neurons and train for \numprint{1000} epoch with patience 200 and a learning rate of \numprint{0.001}.
\end{itemize}


For stochastic algorithms with an explicitly specified seed, we use the run ID as the seed for each of the five runs. While many of these algorithms include multiple configurations, we try to use the best configuration proposed by the authors, and when there is no such clear choice, we use the default configuration included with the implementation.

\subsection{Dataset}

We consider three datasets commonly used in the literature. The first set consists of 10 real-world instances with known ground-truth clusters; we call this dataset \textsc{Ground-Truth} graphs. The machine learning algorithms commonly use these graphs, and the details of the instances are shown in Table~\ref{tab:ground_truth_graphs}. Next, we consider the instances used in the 10th DIMACS implementation challenge on graph clustering; we call this dataset \textsc{DIMACS} graphs. This dataset is popular among the classical modularity optimization methods, and the details of these graphs are shown in Table~\ref{tab:dimacs_instances} in the appendix. Finally, we use a dataset of synthetically generated graphs with node features generated using the attributed, degree-corrected stochastic block model~\cite{adcsbm2022} (ADC-SBM). This generator allows us to explore the algorithm's sensitivity to noise in both the graph and features.

\subsection{Computational Environment}

All experiments are conducted on a machine with an AMD EPYC 9754 128-core processor with 755 GB of memory, running Ubuntu 24.04.3 with Linux kernel 6.8.0-87. For algorithms with compiled software, we use GCC version 13.3.0, and for Python implementations we use Python version 3.12.3.

In order to speed up experiments, we evaluate three algorithms in parallel. For parallel algorithms, we evaluate them both sequentially and using 16 threads. If an algorithm exceeds 250 GB of memory usage on an input instance, it is killed and recorded as \emph{memory limit exceeded} for that graph. Similarly, we assign each algorithm a time limit of 1 hour per input graph. Unlike the memory limitation, we are more leanint with the time limt due to the nature of some learning based algorthms that train a model for a fixed number of iterations. Only if an algorithm overshoots the time limit by more than 50\% do we kill the process and record that instance as \emph{time limit exceeded}.

For algorithms that needs to be told the number of clusters, we either provide the exact number when ground truth labels are known, or 16 clusters otherwise, as is commonly used in the literature. Since several of the algorithms are Stochastic, we perform each experiemtn 5 times and take the best result. In addition to measuring modularity as defined in Section~\ref{sec:preliminary}, we aslo use Normalized Mutual Information (NMI) between the computed clusters and ground-truth labels and F1 scores between adjacent pairs of vertices.

\subsection{Performance Profiles}

For the main comparison between algorithms, we use performance profiles~\cite{perf2002}. A performance profile assigns each included algorithm a non-decreasing, piecewise-constant function. The y-axis represents the fraction of graphs where the objective value is better than or equal to $\tau$ times the best observed objective function value from any algorithm. Reading a performance profile, an algorithm performs well if it achieves lower $\tau$ values for higher fractions of instances.
